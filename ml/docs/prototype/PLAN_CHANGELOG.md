# Plan Changelog: Strip Assay Architecture & Implementation Revisions

This document tracks all conceptual, architectural, and engineering corrections made to the implementation plan before implementing code.

| # | Old Issue in Original Plan | Correction in Revised Plan | Reason | Impact |
|---|-----------------------------|----------------------------|--------|--------|
| 1 | Stated "None currently blocking" under Open Questions. | Replaced with explicit `## Blocking Inputs` section enumerating 6 mandatory external prerequisites. | Real narcotics test validation requires physical chemistry, ground-truth samples, and kit specs that cannot be automated. | Prevents false sense of completion; explicitly delineates automatable pipeline vs. external physical/legal inputs. |
| 2 | Proposed `config/kits/generic_tri_analyte_v1.json` as a usable kit configuration. | Replaced with `config/kits/schema.json` and `config/kits/TEMPLATE_DO_NOT_USE.json` containing only explicit placeholders; added `docs/KIT_CONFIGURATION_REQUIRED.md`. | Inventing chemical reference values (Lab endpoints, CIEDE tolerances) violates forensic integrity and falsifies chemistry. | Forces target-kit reference values to originate only from authoritative manufacturer/laboratory measurements. |
| 3 | Single model state assumed for deployment. | Split models into `models/bootstrap/` and `models/target_validated/`; prohibited deploying bootstrap models to production. | A model trained on surrogate/non-target colorimetry cannot be represented as a validated drug-testing model. | Enforces strict separation between pipeline verification (bootstrap) and certified field deployment. |
| 4 | Soft dataset tier definitions without execution barriers. | Programmatically enforced `dataset_tier` (A/B/C/D) and `target_domain: bool`. If Tier A is missing, pipeline executes in bootstrap mode and explicitly reports target validation unavailable. | Prevents silent leakage or conflation of surrogate colorimetric data with target analyte performance. | Guarantees transparent reporting; prohibits claiming target performance without authentic Tier A data. |
| 5 | Dataset size tracked primarily by raw image count. | Added formal `Minimum Dataset Requirements` tracking unique physical samples, batches, devices, operators, and lighting conditions. | Field test strips photographed multiple times produce highly correlated images that distort real dataset size and diversity. | Establishes scientific dataset quality standards; flags `"insufficient_target_data": true` when diversity criteria are unmet. |
| 6 | Simple random image-level train/test splitting (e.g. 70/15/15). | Replaced with Grouped Data Splitting based primarily on `sample_id` (secondary: `batch_id`, `operator_id`, `device_id`) into a 4-way split: TRAIN, VALIDATION, CALIBRATION, TEST. | Splitting frames of the same physical strip across train and test causes catastrophic data leakage and artificially inflated metrics. | Guarantees test and calibration holdouts are physically independent from training samples. |
| 7 | Single-stage training flow without domain transfer distinction. | Formalized 3-stage domain-transfer strategy: Stage 1 (Bootstrap Pretraining), Stage 2 (Target Fine-tuning), Stage 3 (Unseen Target Evaluation). | If target data is absent, the pipeline stops at Stage 1 and labels the model `BOOTSTRAP / NON-TARGET`. | Prevents premature or fraudulent claims of target analyte detection capability. |
| 8 | Evaluation limited to a single test set. | Added dedicated external generalization tests: Test A (Grouped random), Test B (Unseen batch), Test C (Unseen device), Test D (Unseen lighting), Test E (Unseen operator). | Mobile computer vision often fails under unseen cameras or field illumination; robustness must be empirically measured. | Reports empirical generalization or explicitly flags missing metadata dimensions as `NOT AVAILABLE`. |
| 9 | Validation set reused for threshold tuning and calibration. | Introduced dedicated `CALIBRATION` split distinct from `VALIDATION` and `TEST`. | Tuning CIEDE2000 thresholds and confidence bounds on validation data used for model selection causes subtle over-fitting. | Protects the untouched `TEST` split from any threshold tuning, temperature scaling, or arbitration adjustments. |
| 10 | Temperature scaling mandated automatically. | Made temperature scaling optional: measure Expected Calibration Error (ECE) first; apply scaling only if ECE improves without degrading accuracy. | Prematurely applying post-hoc calibration can distort already well-calibrated probabilities or mask under-confidence. | Ensures calibration adjustments are evidence-based and quantitatively justified. |
| 11 | Automatic deployment of INT8 TFLite model. | Added strict INT8 Acceptance Criteria comparing Keras FP32, TFLite FP32, TFLite FP16, and TFLite INT8; reject INT8 if degradation exceeds tolerance. | Subtle colorimetric shifts in reagent pads can be distorted by 8-bit quantization scale/zero-point truncation. | Protects decision accuracy; falls back to FP16 or flags quantization degradation rather than silently deploying corrupted models. |
| 12 | Vague representative dataset for quantization. | Defined strict representative dataset protocol in `docs/TFLITE_QUANTIZATION.md` drawn only from training/calibration data with multi-lighting/device coverage. | Random or unrepresentative quantization calibration vectors cause poor scale/zero-point estimation for rare color hues. | Ensures INT8 quantization accurately reflects the real distribution of reagent-pad colors. |
| 13 | Hardcoded input resolution assumption (`224x224`). | Dynamic model input shape derived from model metadata/architecture specification (`model_input_shape`). | MobileNetV3-Small supports multiple resolutions (e.g. 192x192, 224x224); hardcoding creates brittle preprocessing couplings. | Allows flexibility and ensures preprocessing dynamically conforms to the active model configuration. |
| 14 | Informal preprocessing assumptions. | Created formal Preprocessing Contract in `docs/MODEL_INPUT_SPEC.md` specifying color space, order, resize, normalization, and tensor dtypes. | Mobile (Android/Kotlin) and Python desktop runtimes easily diverge in color space (RGB vs BGR) or resize interpolation. | Provides a single source of truth for cross-platform equivalence between Python and Android implementations. |
| 15 | Referred to SHA-256 hash chaining as "digital signature". | Corrected terminology to "Cryptographic integrity / hash verification"; reserved "Digital signature" for actual asymmetric key signing. | SHA-256 is an unkeyed cryptographic digest proving data integrity, not non-repudiation or author identity. | Prevents misleading legal and forensic claims in documentation and audit packets. |
| 16 | Claimed pipeline is "compliant with forensic standards". | Replaced with "forensic-oriented validation and documentation" and "designed with evidence integrity and traceability considerations." | Neither software nor kit has undergone formal ISO 17025 / SWGDRUG / AOAC SMPR laboratory accreditation. | Avoids false regulatory compliance claims while maintaining rigorous evidentiary engineering standards. |
| 17 | Datasets lacked formal immutable manifests. | Added `reports/dataset_manifest.json` recording source, URL, checksums, preprocessing versions, and tier tags. | Dataset drift or unversioned raw files prevent experiment replication. | Ensures absolute reproducibility of every data ingestion and processing cycle. |
| 18 | Experiments not isolated or indexed. | Added structured `experiments/EXP-XXX/` directory containing config, metrics, hyperparameters, commit hashes, and model artifacts. | Iterative threshold tuning and training runs require unambiguous provenance. | Enables full lineage tracking from raw data hash to exported TFLite artifact. |
| 19 | Python environment dependencies unpinned. | Added `requirements-lock.txt` and environment specification documenting exact interpreter and library versions. | Python 3.13 and TensorFlow 2.21 have specific wheel and ABI constraints that can break cross-system builds. | Guarantees deterministic, reproducible execution across developer and test environments. |
| 20 | Unstructured monolithic scope. | Reorganized into four priority tiers: P0 (Must Work), P1 (Important), P2 (Nice to Have), P3 (Future). | Complex 29-phase scope risks stalling critical path work on non-essential features. | Clarifies core delivery requirements so P0 pipeline functions work reliably before auxiliary enhancements. |
| 21 | Linear pipeline automation assumed blind execution. | Replaced with Gated Pipeline Automation: Discover → Classify → Verify License → Verify Relevance → Ingest → Validate → Check Readiness → Gated Training. | Blindly training on arbitrary discovered data risks copyright violations and incorrect domain modeling. | Ensures no unverified or non-target data is ever trained or deployed as target models. |
| 22 | Binary readiness check (`training_ready: bool`). | Established 5 discrete Data Readiness States: `NOT_READY`, `BOOTSTRAP_READY`, `TARGET_TRAINING_READY`, `TARGET_VALIDATION_READY`, `PRODUCTION_CANDIDATE`. | Binary flags cannot represent the nuanced transition between surrogate bootstrap testing and certified target readiness. | Programmatically prevents promoting a bootstrap model directly to production candidate. |
| 23 | Aggregated single "accuracy" metric in final report. | Required `FINAL_PIPELINE_REPORT.md` to report distinct, segregated performance tables for Bootstrap, Target, Generalization, and TFLite. | Combining surrogate benchmark accuracy with target accuracy misleads stakeholders regarding actual chemical detection efficacy. | Delivers transparent, uninflated, scientifically rigorous reporting. |
| 24 | Monolithic phase progression. | Structured execution into 13 discrete, sequential phases with gating between discovery, ingestion, bootstrap, and target integration. | Attempting all 29 phases simultaneously leads to cascading failures and unverified assumptions. | Enforces systematic validation at each milestone before proceeding to subsequent stages. |
